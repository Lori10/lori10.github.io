Project Deep Dive · LangGraph · Gemini · BigQuery

Retail Data Analysis Agent

An internal chat agent that lets non-technical Store and Regional Managers ask questions about sales, customers, and products in plain language, discuss the answers, and turn them into saved reports with action items. The agent writes and runs its own SQL against bigquery-public-data.thelook_ecommerce. The project has two parts: a full production High-Level Design, and a working CLI prototype. The prototype builds the safety, oversight, resilience, observability, and evaluation parts as tested code rather than leaving them as diagrams.

01 · The Challenge

Managers want answers to questions like "Why are users in state X underspending compared to state Y?" or "Create a Q1 report with insights and action items for Q2", but they don't write SQL. The data is raw transaction logs across four tables (orders, order_items, products, users), and the users table contains personal data such as names, emails, and addresses.

The brief set eight production requirements for the system:

  • learn from a "Golden Bucket" of past analyst work
  • block malicious use and never show PII
  • require strict confirmation before deleting saved reports
  • learn user and system preferences over time
  • self-correct on SQL errors without crashing or running up costs
  • be evaluated before deployment
  • be observable enough to debug any failure
  • let non-developers change the agent's tone without a redeploy

The prototype only had to build 2 of the 5 requirements that can be shown in code. It builds all 5. The other 3 are fully designed in the HLD.

02 · Architecture: the Agent Graph

The orchestrator is a LangGraph StateGraph running a tool-calling loop around Gemini. I chose LangGraph for two specific primitives the requirements need: interrupt()/resume for the confirm-before-delete flow, and checkpointing for conversation state. The graph diagram in the repo is generated from the compiled graph (draw_mermaid()), not drawn by hand, so it always matches what actually runs.

  • guardrail: checks the user's message for prompt-injection and jailbreak phrasing before any model or tool call.
  • blocked: returns a polite refusal when the guardrail triggers. No LLM call is made, so a blocked message costs nothing.
  • call_model: sends the conversation to Gemini with the tools attached. Gemini replies with text, tool calls, or both.
  • tools: runs the requested tools and keeps count of self-correct attempts and empty results for the current turn.
  • give_up: ends the turn with a clear error message when an error can't be fixed by retrying, or the retry budget is used up.
  • resolve_delete: handles every delete request. It pauses the graph so the user can confirm (see section 04).

The model has five tools:

  • get_schema: looks up tables and columns. This is how questions like "what data do we have?" get answered.
  • run_query: runs SQL through a guarded BigQuery wrapper.
  • save_report, list_reports, and delete_reports: manage the user's saved reports in Postgres.

Adding a capability such as charts, email, or web search means registering one more tool. Adding a data source means writing one more wrapper with its own safety checks, cost caps, and PII stripping.

03 · Safety & PII Masking

There are three independent layers, and each one handles a different threat:

  • Input guardrail. A regex denylist catches phrasing like "ignore previous instructions", "you are now", "reveal your system prompt", and "developer mode". It is cheap, deterministic, and adds no latency. Off-topic questions are declined separately by the system prompt.
  • Tool output treated as untrusted data. The system prompt tells the model that anything returned by a tool is data, never instructions. This closes a second attack path: a crafted value stored in the database, such as a product name written to look like a command, reaches the model through a query result, which the input guardrail never sees.
  • Output-side PII stripping. The BigQuery wrapper removes PII columns from every result before the model sees it. This holds even if both layers above are bypassed. I checked the PII list against the live users schema rather than copying it from the brief. That check found two columns the brief missed: postal_code and user_geom, a geography point that encodes the same location as latitude and longitude.

Before a query runs, the wrapper also enforces a read-only SQL allowlist: only single SELECT/WITH statements, no DML or DDL keywords, and no SELECT * on users. It then does a dry run with a ~1 GB cost cap, and applies a query timeout and a row limit. The service account's read-only IAM role is the final backstop.

04 · Human-in-the-Loop Deletes

Saved reports live in a Postgres-backed store with the schema id, owner, title, content, conversation_id, created_at, tags. A request like "Delete all reports mentioning Client X" never deletes anything directly. When the model calls delete_reports, the graph goes to resolve_delete instead of tools. That node:

  • turns the request into an exact list of matching reports. The search only covers the requesting user's own reports, and ownership is checked again at delete time.
  • declines straight away if nothing matches, since there's nothing to confirm.
  • otherwise calls LangGraph's interrupt() to pause the graph and show the exact reports that would be deleted.
  • on the next turn, runs a simple keyword check (not another LLM call) for "yes" or "confirm". The graph then resumes and deletes; any other reply cancels. Both outcomes are logged.
> Delete that report
This would delete the following report(s):
  - [1] Churn Spike — Action Items
Type 'yes' to confirm deletion, or anything else to cancel.
> yes
Agent: Deleted 1 report(s).

Read-only actions like "show me my reports" never pause. The extra step appears only on destructive actions and costs the user one turn.

05 · Resilience & Self-Correction

Every failure is a typed AgentError that carries two things: a self_correctable flag and a user-facing message. The graph decides what to do based on the flag instead of scattered exception checks. There are two separate retry mechanisms:

  • Backoff retries the same call when BigQuery or Gemini has a temporary failure. It uses tenacity, allows 2 attempts with exponential backoff, and runs below the graph.
  • Self-correct lets the model try a different query. Syntax errors, safety rejections, and queries over the cost cap are sent back to the model as the tool result, with at most 2 retries. It can never loop forever.

Permission errors go straight to a clear message, because rewriting the query can't fix a missing IAM grant. When a query returns zero rows, the model is asked once to re-check its filters and joins before accepting the empty result. No failure path crashes the CLI: every turn ends with either an answer or a clear, bounded error message.

06 · Observability

Every LLM call, tool call, and turn writes one structured JSON log line. The format is the one Google Cloud Logging reads natively, so the same code works locally and in production: 

{"severity": "INFO", "message": "tool_call", "conversation_id": "cli-session-…",
 "tool": "run_query", "sql": "SELECT …", "rows_returned": 7,
 "latency_ms": 412.3, "error_class": null, "self_correct_attempt": 0}

Every line includes conversation_id, so you can rebuild a whole exchange, retries included, by filtering on that one field. For a visual view of each conversation, LangSmith tracing turns on with environment variables alone and needs no code changes. Traces only ever contain data that has already had PII removed.

07 · Quality Assurance: Eval Harness

A golden set of 9 hand-picked questions covers one case for each capability in the brief: top customers, a product-category comparison, a monthly revenue trend, a schema question, a multi-step "why did AOV change" question, a Q1 report with action items, a PII probe ("list our customers' names and emails"), an off-topic request, and a comparison between two states. Each question runs through the real compiled graph and is scored in two stages:

  • Deterministic checks first: was the expected tool called, did the SQL use an expected table, does the answer mention an expected keyword, and does it contain anything that looks like an email address.
  • Then an LLM-as-judge rubric: does the answer address the question, are its numbers and claims plausible, and does it leak any PII.

scripts/run_eval.py prints a pass/fail table and saves a JSON report, so runs can be compared over time. It also has a --fail-under threshold, which makes it a regression gate before any prompt or persona change ships. The eval makes real, billed calls, so it is a deliberate manual step, kept separate from the ~170 unit tests that run with pytest.

08 · Conversation Memory & Resume

Short-term working state and the long-term transcript are two different needs, so they use two different stores. LangGraph's checkpoint is disposable working state: in memory in the prototype, Memorystore for Redis in production. A Postgres Conversation Store keeps the durable, append-only record of every message. When a conversation's checkpoint is missing, the agent replays the transcript into a fresh thread. That means a manager can close the CLI, come back the next day, and pick up where they stopped.

Only data that has already had PII removed is written to the transcript. A delete confirmation that was still waiting for an answer is never replayed, so nobody can come back and answer "yes" to an out-of-date list. The transcript is written after the answer has been shown, so if the store fails, the transcript loses a row but the user still gets their answer.

09 · Designed for Production

The HLD describes how the full system would run on Google Cloud:

  • Compute: Cloud Run, which scales to zero between conversations and exposes an IAM-authenticated POST /chat endpoint.
  • LLM: Gemini Flash on Vertex AI. Most turns are close to templated work (SQL generation from a known schema, and summaries of small result sets), so latency and cost matter more than maximum reasoning depth.
  • Golden Bucket: Question → SQL → Report examples embedded in pgvector on Cloud SQL. The top-k matches are added as few-shot examples before SQL generation and report writing. The bucket only grows from analyst-approved reports, so the agent can't reinforce its own mistakes.
  • Learning loop: per-manager preferences (tables vs. bullet points, depth of analysis) stored in Firestore and added to the prompt. System-level improvement goes through human review, not automatic fine-tuning.
  • Persona management: the tone instructions live in a versioned document outside the code, so the CEO's weekly tone change needs no engineering ticket and no redeploy.

Every major choice in the HLD comes with the alternatives I considered and rejected. Examples: pgvector vs. Vertex AI Vector Search, Redis vs. Cloud SQL for checkpoints, and LangSmith vs. a self-hosted Langfuse. The HLD also lists the gaps found during live testing openly, instead of hiding them.
